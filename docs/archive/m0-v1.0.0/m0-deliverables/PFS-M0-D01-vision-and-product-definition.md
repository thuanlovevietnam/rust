## 1. Vision

A reusable, verifiable system that transforms an initial project idea into an approved Project Foundation — giving humans and AI agents everything they need to understand, implement, maintain and extend the project without undocumented assumptions.

## 2. Objective

Eliminate the need to manually design project structures, documentation systems, architecture specifications, AI agent instructions and quality controls for every new project, by providing a repeatable methodology from idea to approved, verifiable baseline.

## 3. Core Mission (10 capabilities)

1. Understand the project's objectives and requirements.
2. Identify the project's nature, scope and constraints.
3. Analyze functional and non-functional requirements.
4. Design an appropriate architecture.
5. Establish architecture decisions and governance.
6. Generate a structured documentation system.
7. Generate a universal AI Agent system.
8. Establish automated validation and quality controls.
9. Produce a verified project baseline.
10. Support controlled evolution throughout the project lifecycle.

## 4. Product Identity

PFS is an independent **Project Foundation Generator and Governance System**.

It combines four layers (§3.3 of the spec):

1. **Methodology** — how a project should be established.
2. **Project knowledge** — what the project is and how it is designed.
3. **Agent system** — how AI agents interact with project knowledge.
4. **Automation** — how deterministic tasks are executed and verified.

These layers must not be merged into one undifferentiated collection of prompts or scripts.

### 4.1. PFS is not

- A prompt collection.
- A project template repository.
- An AI coding assistant.
- A code generator.
- A documentation generator.
- An agent orchestration framework.

### 4.2. What makes PFS coherent

PFS unifies methodology, structured project knowledge, AI-assisted engineering and deterministic validation in one system. Each part is necessary; none is sufficient alone.

## 5. Fundamental Philosophy

- Architecture before implementation.
- Requirements before architecture.
- Decisions before irreversible changes.
- Documentation as an engineering asset.
- Explicit ownership of important decisions.
- Automation for deterministic tasks.
- AI for reasoning, analysis and design.
- Verification based on evidence.
- Reusable foundations without forcing identical architectures.
- Technology independence at the methodology level.

## 6. Architecture Principle

Provider-independent, modular, extensible.

Rust is an implementation choice for the PFS core automation engine, not a requirement imposed on projects generated by PFS (spec §13.2). The methodology and generated project formats remain independent of the engine's implementation language.

## 7. Value Proposition

| Without PFS | With PFS |
|---|---|
| Each project re-derives its foundation ad hoc | Foundation produced by a repeatable, gated methodology |
| Implicit, undocumented assumptions | Explicit, traceable requirements → architecture → decisions |
| Agent output trusted on claim | Verification requires observable evidence |
| Approval implicit or skipped | Explicit decision ownership and approval boundaries |
| Documentation drifts and conflicts | Single source of truth with integrity checks |

## 8. Success Definition for M0

M0 succeeds when the methodology defined here is complete, consistent, traceable to the spec, independently reviewed, and accepted by the project owner — not when code is written. M0 does not authorize implementation of the Rust engine.

## 9. Explicitly Out of Scope for the Product at M0

See PFS-M0-SPEC-001 §14 (Non-Goals of M0) and PFS-M0-D11 §4 (milestone boundaries). No engine implementation, GUI, provider integration, MCP server, orchestration, database or full template library is authorized by M0.
